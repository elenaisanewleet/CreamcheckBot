# CreamcheckBot (@creamcheck_bot)

Телеграм-бот, который оценивает риск комедогенности косметики по фото упаковки
или по названию продукта.

Как работает:

1. **Шаг 1** — модель (OpenAI Responses API + веб-поиск) распознаёт продукт и находит
   полный состав INCI. Флаги комедогенности проставляет **код**, а не модель:
   строго по фиксированной базе в `agent/comedogen_base.py`. Уровень риска считает
   `calc_risk_level_strict()` в `bot/bot.py`.
2. **Кнопка «🧾 Посмотреть состав»** — полный список ингредиентов с отметками.
3. **Кнопка «📘 Подробнее»** — шаг 2: пояснения по комедогенам и рекомендации,
   привязанные к конкретным компонентам этого состава.
4. **Кнопка «🧩 Что делает каждый компонент»** — разбор всего состава INCI,
   разложенный по функциональным группам.
5. **Кнопка «❓ Что спросить у врача»** — три вопроса дерматологу, выросшие
   из этого состава, и прямая ссылка на приём.

## Разбор состава и путь к врачу

### Почему так

Разбор состава — это не консультация. Подойдёт ли средство конкретной коже,
зависит от того, чего бот знать не может: типа кожи, состояния барьера,
остального ухода, назначенных препаратов, сезона. Поэтому финальный экран —
не дисклеймер в подвале, который взгляд давно пропускает, а конкретные вопросы,
на которые честно ответит только живой врач.

### Честная неполнота, а не умалчивание

Задача — чтобы человек захотел спросить врача. Сделать это можно двумя способами,
и выбран второй:

- ❌ знать и намеренно недоговаривать, подталкивая к записи;
- ✅ называть вслух настоящую границу знания.

Граница реальна: про вещество есть данные (что это, как ведёт себя у людей
вообще), а как оно поведёт себя **на этой конкретной коже** — не знает никто,
кроме врача на осмотре. Поэтому каждое пояснение состоит из трёх частей:

```
🟠 Hydroxypinacolone Retinoate · №3
Производное витамина A. Действует мягче чистого ретинола,     ← что известно
но в первые недели часто даёт сухость.
🩺 Совместим ли он с тем, чем ты уже пользуешься, и с какой    ← что зависит
   частоты начинать — зависит от состояния барьера.              от человека
```

Третья часть (`ask`) заполняется только там, где вопрос настоящий: комедогены,
активы, отдушки и аллергены, компоненты на первых позициях. Для воды
и загустителей она пустая — выдуманный вопрос обесценивает настоящие.

### Ничего не выдумывать

У каждого компонента модель обязана проставить отметку достоверности:

| Отметка | Что значит | Видит ли пользователь |
|---|---|---|
| `src=web` | проверено поиском в этом разговоре | нет |
| `src=known` | общеизвестное вещество, сомнений нет | нет |
| `src=thin` | надёжных данных мало, источники расходятся | **да** |

`thin` выводится прямо в карточке: «Надёжных данных по нему немного —
додумывать не буду». Признание полезнее правдоподобной выдумки, и оно само
по себе повод спросить врача. Незнакомое значение отметки отбрасывается,
чтобы не выдать мусор за достоверность.

Веб-поиск для этого шага включён по умолчанию (`INGREDIENTS_WEB_SEARCH=true`,
до 8 запросов): редкие торговые названия и растительные экстракты модель
обязана искать, а не вспоминать.

### К врачу — с любого экрана

Кнопка к дерматологу есть на каждом шаге, включая самый первый: разбор состава
не отвечает на вопрос «подойдёт ли это мне», и предложить живого специалиста
уместно сразу. Где вопросы уже собраны — ведёт на них, где ещё нет — прямой
ссылкой на врача. У карточки группы отдельная кнопка «N вопросов по этой
группе»: они ближе к тому, что человек только что прочитал, чем общий список.

### Как раскрывается состав

В составе обычно 25–45 ингредиентов, и кнопка на каждый превратилась бы
в пролистывание шести экранов. Вместо этого компоненты разложены по девяти
функциональным группам (`agent/groups.py`): эмоленты и масла, силиконы,
увлажнители, активные, очищающие, консерванты, отдушки и экстракты,
текстура и стабильность, остальное. Пустые группы не показываются.

Каждый компонент попадает ровно в одну группу и получает пояснение: что это
такое, зачем он в формуле и о чём говорит его позиция в списке. Компонент,
который модель пропустила, не теряется — он остаётся в списке без пояснения.

Группу присваивает модель, но **уровень комедогенности по-прежнему проставляет
код** по фиксированной базе — на оценку риска разбор не влияет.

### Сколько это стоит

Разбор считается **лениво**: только когда человек нажал кнопку. Поэтому
«Подробнее» открывается ровно так же быстро, как раньше. Результат кэшируется
наравне с остальными шагами, так что повторный разбор того же состава —
и переходы между группами внутри одного разбора — бесплатны и мгновенны.

Ответ модели разбирается построчно, а не как JSON: если он обрежется по лимиту
токенов, уцелевшие строки всё равно попадут в карточки, тогда как оборванный
JSON пропал бы целиком.

### Настройки

`INGREDIENTS_ENABLED` выключает фичу целиком, `INGREDIENTS_WEB_SEARCH` —
только веб-поиск внутри неё, `DOCTOR_USERNAME` меняет адресата кнопки записи.
Подробности — в `.env.example`.

### Проверка качества ответов

`pytest` проверяет код, но не то, насколько осмысленно пишет модель. Для этого
есть отдельный скрипт — он прогоняет полный путь на настоящих продуктах,
печатает все экраны и считает две метрики:

```bash
python -m tools.live_check "CeraVe Moisturising Cream" "La Roche-Posay Effaclar Duo+"
```

- **привязаны ли рекомендации к составу** — каждый пункт помечается `✓` или
  `✗ ОБЩЕЕ МЕСТО`, если в нём не назван ни один компонент и ни одна позиция;
- **сколько компонентов получили пояснение** из общего числа в INCI.

Плюс время, токены и стоимость по каждому из трёх вызовов. Запускать после
любой правки промптов: расходует API (три вызова модели на продукт).

## Запуск

```bash
cp .env.example .env      # заполнить TELEGRAM_BOT_TOKEN и OPENAI_API_KEY
pip install -r requirements.txt
python -m bot.bot
```

Docker:

```bash
docker build -t creamcheck .
docker run -d --name creamcheck \
  --env-file .env \
  -p 10000:10000 \
  -v creamcheck-data:/app/data \
  --restart unless-stopped \
  creamcheck
```

> **Важно:** том `/app/data` обязателен — там лежат статистика, логи, кэш
> и правки базы комедогенов. Без тома всё это обнуляется при каждом
> пересоздании контейнера.

### Деплой одной командой

На сервере, из папки с репозиторием:

```bash
./deploy.sh              # обновить код и перезапустить
./deploy.sh --key        # то же плюс сменить OPENAI_API_KEY
./deploy.sh --no-pull    # пересобрать из того, что уже лежит локально
```

Скрипт идемпотентен — гонять можно сколько угодно раз. Что он делает:
подтягивает `main`, проверяет что заполнены обязательные переменные, собирает
образ, **гасит прежний контейнер до старта нового** (два процесса на одном
токене Telegram конфликтуют за long polling), поднимает новый с томом данных
и ждёт ответа `/health`. Если контейнер упал — покажет хвост лога.

`--key` спрашивает ключ с выключенным эхом, поэтому он не попадает ни на экран,
ни в историю команд. Прежний `.env` сохраняется рядом как `.env.bak.<дата>`,
остальные переменные не трогаются.

Тесты:

```bash
pip install -r requirements-dev.txt
pytest
```

## Кто пользуется ботом: статистика и логи

Бот пишет каждое действие в SQLite (`data/analytics.db`): кто, когда, что прислал,
какой получился риск, сколько это заняло и во сколько обошлось.

### Скрытые команды в Telegram

Видны **только** админам из `ADMIN_IDS` (по умолчанию Лена `41082373` и Лиза `228174255`).
Для всех остальных этих команд не существует — бот просто молчит.

| Команда | Что показывает |
|---|---|
| `/stats` | Люди (всего / сегодня / неделя / месяц), разборы, кэш, ошибки, расход |
| `/users` | Кто чем пользуется: разборы, фото, текст, «Состав», «Подробнее» |
| `/flow [N]` | Живой поток последних N событий |
| `/errors` | Последние ошибки с описанием |
| `/logs [N]` | Последние строки лога (длинные — файлом) |
| `/export` | Все события в CSV |
| `/dash` | Ссылка на веб-дашборд с ключом |
| `/cache`, `/cache_clear` | Состояние кэша и его очистка |
| `/panel` | Панель с кнопками: дашборд, отчёты, база комедогенов |
| `/base` | База комедогенов: просмотр и правка |
| `/adminhelp` | Эта же таблица внутри бота |

> `/base` раньше была открыта всем и показывала весь справочник. Теперь она
> админская. Если команда была заведена в BotFather — её стоит оттуда убрать,
> иначе она продолжит подсказываться пользователям при наборе (нажатие
> при этом ничего не даст).

## Правка базы комедогенов из Telegram

`/panel` → **🧪 База комедогенов** → список → кнопка на компоненте.
Добавление — кнопкой **➕**, дальше бот ждёт название одним сообщением.

### Эталон нельзя испортить

`agent/comedogen_base.py` — неизменяемый эталон, код его не трогает никогда.
Правки складываются отдельным слоем в SQLite, рабочая база собирается как
«эталон плюс правки» (`bot/comedogen_store.py`). Отсюда три следствия:

- **Сбросить к эталону** возвращает выверенный список в любой момент.
- Каждая правка подписана автором и временем, любую можно отменить
  по отдельности — записи не удаляются, отмена это `active = 0`.
- Если том с данными потеряется, бот вернётся к эталону, а не останется
  без базы вообще.

Пока правок нет, `effective()` отдаёт ровно эталонные объекты — риск считается
в точности как до появления этого слоя.

### Что происходит при правке

Правка **меняет вердикты для всех пользователей**, поэтому:

- кэш готовых разборов сбрасывается автоматически — иначе люди продолжат
  видеть оценки, посчитанные по прежней базе;
- удаление требует подтверждения, а в подтверждении показывается название;
- кнопка несёт подпись названия, так что при рассинхроне списка (кто-то
  правил параллельно) нажатие отклоняется, а не удаляет соседний компонент.

Правило про `wax` — отдельное, не по списку, — тоже подчиняется базе:
убрали `wax` из базы, и `Candelilla Wax` перестаёт отмечаться.

Правки требуют `ANALYTICS_ENABLED=true` — без базы данных их негде хранить,
и админка честно об этом пишет.

### Веб-дашборд

```
http://<адрес сервера>:10000/dash?key=<DASHBOARD_TOKEN>
```

Живая страница: аудитория (всего людей, DAU/WAU/MAU, новые, возвращающиеся),
разборы, доля ответов из кэша, среднее время, распределение уровней риска,
частые продукты, таблица людей, поток событий и хвост лога.
Обновляется сама раз в 30 секунд, работает и с телефона.

Доступ закрыт токеном `DASHBOARD_TOKEN`. Если его не задать, токен сгенерируется
при старте и попадёт в лог, но будет меняться при каждом перезапуске — лучше задать свой.
Health-проверки `/` и `/health` остались открытыми и работают как раньше.

> Дашборд отдаётся по HTTP без шифрования. Не публикуй ссылку с ключом.
> Если бот доступен из интернета — лучше закрыть порт 10000 файрволом
> и ходить через SSH-туннель, либо поставить nginx с HTTPS.

Служебные ручки (все требуют `?key=`):
`/api/stats`, `/api/events`, `/api/logs`, `/export.csv`.

## Что было сделано для скорости и экономии

| Изменение | Эффект |
|---|---|
| Проверка ссылки-источника убрана с «горячего» пути | −до 6 секунд на **каждый** разбор. Раньше бот ходил на сайт-источник и ждал ответа **до** того, как показать результат, хотя сама ссылка нужна только на экране «Состав». Теперь проверка идёт в фоне, а её результат кэшируется. |
| Кэш готовых разборов (SQLite, 30 дней) | Повторный запрос того же продукта — мгновенно и **бесплатно**. Ключ нормализован: «CeraVe Cream» и «cerave   cream» — одно и то же. Разбор по фото дополнительно сохраняется под распознанным названием, поэтому текстовый запрос того же средства тоже попадает в кэш. |
| Кэш шага 2 («Подробнее») | Пояснение по уже разобранному составу выдаётся без обращения к модели. |
| Плашка «Анализирую фото…» шлётся параллельно со скачиванием | Человек видит реакцию бота на ~секунду раньше. |
| Один HTTP-клиент на процесс | Раньше на каждое фото создавался новый клиент и заново делался TLS-хендшейк. |
| Альбом фото → **один** запрос к модели | Раньше 3 фото = 3 отдельных разбора и 3 ответа. Теперь лицевая сторона и оборот с составом уходят вместе — точнее и втрое дешевле. |
| Один тяжёлый разбор на человека одновременно | Быстрые повторные отправки больше не удваивают счёт за API. |
| `prompt_cache_key` | Системный промпт (~2500 токенов) переиспользуется по цене кэшированного ввода — примерно в 10 раз дешевле. |
| Ограничение длины текстового запроса | Защита от «простыней» в промпте. |

Ничего из этого не меняет тексты ответов и логику оценки риска.

### Ручки для дальнейшего ускорения (по умолчанию выключены)

Всё это в `.env`, каждая настройка меняет поведение — включай по одной и проверяй:

- `STEP2_WEB_SEARCH=false` — шагу 2 веб-поиск почти не нужен, состав уже найден
  на шаге 1. Заметно дешевле и быстрее «Подробнее».
- `STEP1_MAX_TOOL_CALLS=6` (сейчас 10) — меньше веб-поисков на разбор.
- `STEP1_REASONING_EFFORT=low` — самый сильный рычаг по скорости, но может
  просесть качество поиска состава. Проверять на своих примерах обязательно.
- `IMAGE_MAX_SIDE=1024` — сжатие фото перед отправкой (нужен Pillow).
  По умолчанию выключено: мелкий шрифт состава читается лучше в оригинале.
- `RATE_LIMIT_PER_HOUR=20` — потолок разборов на человека в час.

## ⚠️ Два расхождения промпта и кода (решение за Леной и Лизой)

Найдены при написании тестов. **Не исправлены по умолчанию**, потому что они
меняют уровень риска у части продуктов — а это то, что видит пользователь.

1. **Beeswax не отмечается как жёсткий комедоген.**
   Промпт прямо называет `beeswax` примером правила «wax в названии → жёсткий»,
   но код ищет `wax` только как отдельное слово. Итог:
   `Candelilla Wax` → 🔴 отмечается, а `Beeswax`, `Synthetic Beeswax`
   и `Cera Alba` (это INCI-название пчелиного воска) → не отмечаются.

2. **Polysilicone-11 не отмечается как условный.**
   Промпт приводит его примером частичного совпадения по `sil`, но код требует
   отдельного слова — иначе он ловил бы `Silica`.

Обе правки включаются одной переменной:

```
COMEDOGEN_MATCH_V2=true
```

При этом `Silica` по-прежнему не отмечается, а нейтральные ингредиенты
не затрагиваются — это покрыто тестами (`tests/test_classification.py`).
Обе правки **повышают** уровень риска у части средств, поэтому включать
стоит после проверки на реальных составах вместе с Лизой.
